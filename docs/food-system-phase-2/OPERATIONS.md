## Admin bulk importer
Open /admin/catalog-import; authenticate using the existing admin password (memory only). Upload CSV or JSON, then Validate and preview. Apply requires the exact normalized checksum and current catalog revision. Batches: 1–100 records, 200 KB content. The endpoint rejects edits to existing IDs, unknown categories, duplicate canonical/source identities, undocumented rights, invalid reference units, negative/nonfinite nutrition and unexplained large macro-energy discrepancies. No new migration is needed: it uses the existing catalog, audit and import tables.

JSON: array of validated food objects (use data/catalog/phase2-reviewed.json as the example). CSV headers:
`id,en,ar,ku,categoryId,calories,protein,carbs,fat,referenceAmount,nutritionUnit,sourceType,sourceDescription,fdcId,license`
Optional headers: canonicalId, category, aliases (pipe-separated), portions (JSON), url, brand, product, flavor, region, gtin, rightsEvidence, commercialReuseCleared, energyExplanation. Quote JSON/comma-containing cells using RFC4180. Values apply to the stated reference quantity, not automatically 100 g. kg/L normalize reference AND portion amounts to g/mL. Never infer density. All three names are required; only independently verified conversions should be entered.

Non-USDA sources require a license plus documented commercialReuseCleared=true and rightsEvidence. This is an administrator attestation, not automatic legal clearance. USDA references require a valid FDC identifier and CC0-1.0. Evidence is retained for administrators; private rights evidence is omitted from public snapshots.

Apply is an advisory-lock-protected transaction. Failure rolls back the entire batch and audit. Repeating a checksum is idempotent. Download the remediation manifest after apply. To retract an addition, use the existing authenticated catalog PUT with {food, revision, enabled:false} from the manifest. A changed revision returns 409; review it rather than overwriting. Do not DELETE foods or rewrite historical meal nutrition. Category/alias changes have before/after audit records and require separately reviewed reverse edits.

## Optional two-photo scanner
The top image remains required and the side view optional. Review, retake and remove work before submitting. Both images together are limited to 1 MiB (server request remains bounded to 1.5 MB including base64). Existing single-photo clients are unchanged. The prompt treats both views as one meal; no food should be counted twice. Measurements are optional: container capacity up to 20000 mL, depth up to 100 cm, weighed food mass up to 10000 g. Container capacity/depth do not prove the food volume or density. Identity and quantity corrections remain user-confirmed; catalog mass corrections use the verified reference and reject volume-to-mass guessing. Photos alone cannot establish exact weight. No live Gemini requests were used for Phase 2 verification, so multi-angle accuracy on measured real meals remains unverified.
